# 公開前チェックリスト

ドラフトを書き終えたら、Skill 自身が以下を順に確認する。ユーザーに返す出力の末尾に **チェック結果（✅ / ⚠️ / ❌）** を併記する。⚠️ や ❌ が残っている場合は、ユーザーに確認を促す。

## A. 機密情報・公開可否

- [ ] 社内システム名・社内ツール名・プロジェクトコードネームが出ていないか
- [ ] 顧客名・取引先名・パートナー名が出ていないか
- [ ] 個人名は「実名公開OK」と明示された場合のみ使われているか
- [ ] スクショ・図に社内固有名詞・個人情報・URL・トークンが映り込んでいないか
- [ ] 性能数値・トラフィック量・売上関連の具体数値を不用意に出していないか
- [ ] インシデント・障害の固有情報（日付・影響範囲）を出していないか
- [ ] 「社外公開NGの内容」に挙げられた要素が記事に残っていないか

判断に迷うものは [DISCLOSURE_GUIDE.md](./DISCLOSURE_GUIDE.md) を参照。**迷ったらカットする** を原則とする。

## B. 内容の正確さ

- [ ] 技術的に誤解を招く断定（「絶対安全」「常に最速」など）がないか
- [ ] 引用したライブラリ・サービスのバージョン・仕様が現時点で正しいか（怪しければ「確認が必要」事項に入れる）
- [ ] OSSやプロダクトの用語が一般的な表記になっているか（例: `openTelemetry` → `OpenTelemetry`）
- [ ] 推測で補った箇所がないか。あれば「確認が必要」事項に明記したか

## C. 構成と読みやすさ

- [ ] 導入文に「URBAN HACKS のバックエンドエンジニアコミュニティで技術共有会を開催している」旨があるか
- [ ] 初回記事の場合、「シリーズ初回であること」が明示されているか
- [ ] 2回目以降の場合、シリーズの継続感（第N回 / 前回への言及）があるか
- [ ] 各発表が「内容 → 面白いポイント → 学び」の構成になっているか（単純な羅列になっていないか）
- [ ] 全体を通した所感と次回へのつなぎがあるか
- [ ] 見出しレベル（H2 / H3）が一貫しているか。H1 は使っていないか

## D. トーン・広報視点

- [ ] カジュアルすぎず堅すぎないトーンに揃っているか
- [ ] 「最強」「神」「爆速」など過剰な煽りがないか
- [ ] 他社・他技術を貶める表現がないか
- [ ] チームの学習文化・技術への向き合い方が伝わる文章になっているか
- [ ] 採用広報的観点で「ここで働くとどんな学びがあるか」がさりげなく感じられるか

## E. Zenn 体裁

- [ ] フロントマター案を併記しているか（`title`, `emoji`, `type`, `topics`, `published: false`）
- [ ] `topics` は 5 個以内・小文字・ハイフンなしになっているか
- [ ] `published` が `false` になっているか（誤って `true` で出していないか）
- [ ] 画像を使う場合、`/images/<slug>/<file>` の参照になっているか（[AGENTS.md](../../../AGENTS.md) 参照）
