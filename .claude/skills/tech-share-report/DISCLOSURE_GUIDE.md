# 社外公開可否の判断観点

社外向け技術広報記事として書く以上、**「迷ったらカット」「明示OKだけ採用」** を原則とする。NGリストに該当しなくても、判断に迷えばユーザーに確認する。

## 基本ルール

1. **明示的に「社外公開してよい」と書かれた内容のみ採用する**
2. NG欄に書かれていなくても、以下「自動NG項目」に該当するものはデフォルトでカットする
3. 迷ったら **記事に入れず、ユーザー確認に回す**（「確認が必要」事項リストに入れる）

## 自動NG項目（書かれていなくてもカット）

### 1. 社内固有名詞

- 社内システム名・サービスコードネーム・社内ツール名
- プロジェクト名・チーム名（部署名含む）
- 社内独自のリポジトリ名・ブランチ名・モジュール名

→ 一般語に翻訳する。例: 「社内の予約管理サービス Foo」→「ある業務系サービス」

### 2. 顧客・取引先・パートナー情報

- 顧客企業名・案件名
- 取引先・パートナー企業名
- SaaS 契約状況に紐づく具体的な金額・規模

### 3. 個人情報

- 実名（明示OKの場合のみ可）
- 顔写真・SNSアカウント
- 社員番号・連絡先

### 4. 未公開・非公開情報

- リリース前の機能・仕様
- 構成図（社内ネットワーク・社内インフラの実構成）
- 内部 API のスキーマ・エンドポイント
- 環境変数・シークレット・トークン（**絶対に**載せない）

### 5. インシデント・障害

- 障害の具体的な発生日時・影響範囲
- 顧客影響・損失金額
- ポストモーテム本文（明示的に外向け版が用意されている場合のみ可）

### 6. 数値・指標

- トラフィック量・QPS・ユーザー数の具体数値
- レイテンシ・SLO の具体数値（一般化した「ミリ秒オーダー」程度の表現はOKの場合あり、ユーザー確認）
- 売上・コスト・契約金額

### 7. 法務・コンプライアンス

- 法務レビュー未通過の比較ベンチマーク（他社製品・他OSSとの優劣を断じるもの）
- ライセンス上、引用条件があるコード片（条件を満たさない引用）

## 判断のグレーゾーン（ユーザー確認に回す）

- 「OSS の使い方」レベルの内容だが、社内の使い方の文脈が混ざっている
- 公開済みリンク（公式ドキュメント・公開ブログ）に書かれている内容と社内の取り組みの境界が曖昧
- 「業界では一般的だがウチの解釈が入っている」設計判断
- 発表者の所属を「URBAN HACKS のバックエンドエンジニア」と書くか「メンバーの一人」とぼかすか

## 個人名の扱い

- **デフォルト**: 個人名は出さない。「バックエンドエンジニアの一人」「メンバーの一人」と表記
- **OKケース**: 入力テンプレで `実名公開OK: yes` と明示された場合のみ実名を使う
- 実名を使う場合も、所属チーム名や社員番号などの追加情報は出さない

## コード・図の扱い

- コード片は「OSS の API そのまま」「公開ドキュメントから引用」レベルなら可
- 社内コードベースからの抜粋は **原則NG**。書きたい場合は十分に一般化・抽象化し、ユーザー確認に回す
- 図・スクショは社内固有名詞・社内URL・トークンが映っていないことを確認。確認できない場合は載せない

## 確認が必要事項の書き方

判断に迷ったら、ドラフトに入れずに「確認が必要」事項リストに以下のフォーマットで残す。

```markdown
- 【要確認】発表2の「〇〇の構成図」は社外公開してよいか。社内サービス名が含まれているように見える。
- 【要確認】発表3の発表者名 A さんは実名公開してよいか。入力テンプレで明示されていなかった。
```
