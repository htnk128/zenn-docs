## 3Dプリンターを買った話

発表者: tai さん

3Dプリンターで身の回りのものを自作してみると、デジタル上の設計が現物になるまでに、どんな工夫や試行錯誤があるのでしょうか。購入後に作ったものや、モデリングから印刷までの流れが紹介されました。

### どんな内容だったか

最初は公開されているモデルを印刷して使い方を覚え、その後はCADで自作したモデルにも挑戦したそうです。たとえば、デスク周りで使うケースなど、生活の中で使うものを自分で設計して形にしていました。

基本的な流れは、CADでモデルを作り、3Dデータをエクスポートし、スライサーで各層の形や印刷設定を決めてプリントする、というものです。設計には[Autodesk Fusion](https://www.autodesk.com/jp/products/fusion-360/overview)を使い、モデルを印刷用のデータに整えていきます。後日談として、生成AIを相談相手にしながらPythonで3Dモデルデータを作る試みにも挑戦したそうです。

### 技術的に面白いポイント

CADでのモデリングには、プログラミングと似た面白さもあるとのこと。作業の履歴をたどってモデルを変更できるため、少しずつ形を調整しながら完成度を上げていけます。一度モデルを作れば繰り返し印刷できる一方、最初のモデリングには手間がかかるため、何を作るかを考える時間も大切です。

### 盛り上がったポイント

印刷には思った以上に時間がかかることや、完成間近で失敗したときの悔しさなど、実際に使ってみて分かる話に広がりました。また、積層方向によって強度が変わるため、飾るものと実用品では設計時に考えることが違う、という点も話題になりました。カラー印刷や3Dスキャナーなど、次に試してみたい選択肢にも関心が集まりました。

### 学び

3Dプリンターは、設計したものを繰り返し作れる一方で、モデルを作るまでの試行錯誤も含めて楽しむ道具なのだと感じました。現物を見るときに、形や作り手の工夫に目が向くようになるという話も印象的でした。

## 最近の AWS DevOps Agent 事情

発表者: yossy さん

AWS DevOps Agentの用途が、障害調査から定常的な運用タスクへと広がっている様子を紹介する発表です。発表資料は2026年9月6日時点の情報を中心にまとめられていました。

### どんな内容だったか

AWS DevOps Agentの中心的な機能として、アラートやインシデントをきっかけに、関連する情報を調べて原因候補や対応案をまとめる調査機能が紹介されました。さらに、用途に応じて指示や使えるツール、スキル、メモリを設定する「Custom Agents」を使うことで、セキュリティの傾向分析、クラウドコストの確認、SLOの定期チェックのような運用タスクにも応用できます。[AWSの公式ドキュメント](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-custom-agents-index.html)でも、カスタムエージェントの設定や実行方法が案内されています。

### 技術的に面白いポイント

複数のデータソースにまたがる情報収集や分析をAgentに任せる場合、どの情報を参照させ、どの範囲まで調べさせるかが重要になります。調査を深く続けるほど費用も増えるため、用途や終了条件を決めておく視点も共有されました。[AWS DevOps Agentの料金は、タスク中にAgentが稼働した時間に応じて発生します](https://aws.amazon.com/devops-agent/pricing/)。

また、リソースの作成や変更を伴う操作は初期状態では無効で、実行には人の承認が必要です。調査・提案と実際の変更を分けて運用する考え方は、Agentを業務に取り入れる際の大切な判断軸です。[Directed Actionsの仕組み](https://docs.aws.amazon.com/devopsagent/latest/userguide/working-with-devops-agent-working-with-directed-actions.html)では、承認や操作の記録についても説明されています。

### 盛り上がったポイント

Agentに任せる範囲や、調査に使う情報をどう用意するかが話題になりました。最初から広く任せるのではなく、調査対象や実行条件を絞り、結果を人が確認する形から試すのがよさそうです。

### 学び

運用の定型作業をAgentに任せるときは、モデルやプロンプトだけでなく、参照できる情報と実行できる操作の範囲を一緒に設計する必要があると感じました。AWS DevOps Agentの機能は継続的に更新されているため、最新情報は[公式の更新履歴](https://docs.aws.amazon.com/devopsagent/latest/userguide/whats-new.html)で確認できます。

## 最近のCloud Runについて

発表者: yassu さん

Cloud Runにはどのような実行方法があり、用途に応じてどう選ぶとよいのでしょうか。新しいリソースタイプやスケーリング設定を中心に、それぞれの特徴と使い分けが紹介されました。

### どんな内容だったか

Cloud Runの実行モデルは、Webサービス向けのServices、イベント処理に使えるFunctions、処理を実行して終了するJobs、HTTPリクエストを受けない常駐処理向けのWorker poolsなどに広がっています。さらに2026年8月には、長時間動く単一のコンテナを個別に管理するCloud Run instancesがPreviewとして登場しました。[Google Cloudのリリースノート](https://docs.cloud.google.com/run/docs/release-notes)と[Cloud Runの概要](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run)で、各リソースタイプの特徴を確認できます。

### 技術的に面白いポイント

Cloud Run instancesは、個別に起動・停止でき、固有のURLを持つ単一インスタンスとして動きます。水平オートスケールを前提とするサービスとは違い、長時間稼働するAgentや、単一プロセスの常駐サーバーなどが用途として挙げられています。

Servicesの最小インスタンス数には、サービス全体に設定する方法とリビジョンごとに設定する方法があります。リビジョン単位で最小数を設定すると、トラフィックがないリビジョンでもTraffic Tagが残っている間は起動状態が維持され、費用が発生することがあります。Googleはサービス単位の設定を推奨しています。[最小インスタンス数の公式ガイド](https://docs.cloud.google.com/run/docs/configuring/min-instances)には設定範囲や注意点がまとめられています。

また、CPUや同時リクエスト数を基準にスケーリングする際の目標値も調整できます。目標値を低くすると早めにスケールしやすくなり、余裕を持たせられる一方で、インスタンス数や費用が増える可能性があります。[Custom scaling controls](https://docs.cloud.google.com/run/docs/configuring/scaling-controls)はPreviewの機能です。

### 盛り上がったポイント

新しい実行モデルをどんな処理に使えるかに加え、最小インスタンス数やTraffic Tagの設定が費用にどう影響するかも話題になりました。Cloud Runの選択肢が増えたことで、処理の性質に応じて構成を見直すきっかけになりそうです。

### 学び

新機能の有無だけで実行環境を選ぶのではなく、処理が短時間で終わるのか、HTTPリクエストを受けるのか、長時間動き続けるのかを先に整理することが大切です。実行モデルを使い分けることで、構成や運用の考え方も変わってきます。
