## ConfluenceからNotionへの移行ツール開発

発表者: u3 さん

社内の情報管理ツールをConfluenceからNotionへ移行するにあたり、バックエンドエンジニアがサポートメンバーとして移行ツールの開発に関わった取り組みの紹介です。AIを全面活用したアクセル全開の開発スタイルが印象的でした。

### どんな内容だったか

既存の OSS ツールを活用しつつ、Confluence 独自タグの変換やファイル添付のカスタム対応など、標準ツールでは補えない部分を独自実装したとのことです。プロジェクトはバックエンドエンジニア数名でサポートしており、PR・人によるコードレビューを挟まず、手元で動作確認して main へマージするというスタイルで進めています。

「このプログラム自体は移行が終わったら不要になる」という性質を逆手に取り、コードレビューやロジック確認を AI に任せ切るアクセル全開の実験として割り切っています。AI が苦戦しそうな気配を感じたときだけ、ディレクトリ構成を眺めてリファクタリング可能なポイントを AI に探させる程度の関わり方、という話が面白かったです。

また、Notion Workers（Notion のサーバー上で TypeScript のカスタムコードを実行できるサーバーレス実行環境）を活用して、移行後のデータ連携自動化も試みているとのことでした。

### 技術的に面白いポイント

- **使い捨てを前提にした開発スタイル**: 「動いたら終わり」な性質のプロジェクトで AI を全力活用する判断軸が参考になる
- **Notion Workers の活用**: Notion Workers を使い、プロジェクト関連データをDB自動保存するといった拡張も試みている

### 盛り上がったポイント

「AI全任せでコード生成・PR・人によるコードレビューを挟まず手元で確認して main へマージ」というストロングスタイルへの驚きと共感が集まりました。「本番運用するシステムなら絶対やらないけど、使い捨てツールなら AI 任せアクセル全開でいい実験」という判断の明快さが議論のポイントになっていました。

### 学び

「使い捨てかどうか」でAIへの委任度を意図的に変える判断は、AI活用の実践的な使い分けとして参考になります。本番システムでは慎重さが求められる一方で、こういった実験的プロジェクトで思い切り試すことで、AIとの協働ノウハウが蓄積されていくのだと感じました。

## Claude Code と Codex の compact 比較

発表者: kenny さん

AIコーディングツールが長い作業でコンテキストが膨らんだときに行う「compact（コンテキスト圧縮）」について、Claude Code と Codex の設計の違いを詳しく調べた内容です。表面上は同じ名前の機能でも、内部設計の方向性が異なることが浮き彫りになりました。

### どんな内容だったか

compact とは、長いエージェント作業で膨らんだ会話履歴を短くして次のターンを続けられるようにする機能です。単なるトークン節約ではなく、compact 後のエージェントは圧縮後に残った情報をもとに判断するため、「何を残すか」が作業品質に直結します。

Claude Code の `/compact [instructions]` は、ユーザーが「何を優先して残すか」を指示できる設計になっており、compact を「人間が引き継ぎメモの観点を与えられる処理」として扱えます。hooks（PreCompact / PostCompact）との組み合わせで、compact 前後の状態管理も可能です。一方 Codex は `/compact` と auto compact を持ちますが、発表者がローカルの auto compact 実例を調べた環境では「残す user message 群 + 暗号化された compaction item」として保存されており、圧縮内容そのものは不透明でした。

### 技術的に面白いポイント

- **Claude Code の可観測性**: compact の境界・前後のトークン数・削減量・実行時間がローカル履歴に残り、追いやすい
- **Codex の compaction item は API 側の opaque payload**: 発表者の調査環境では、ローカル履歴に残る `encrypted_content` はクライアントが暗号化するのではなく、API から返ってくる不透明な文字列をそのまま保持しているように観測されました

### 盛り上がったポイント

「MCP を入れすぎるとコンテキストを食う」「CLAUDE.md を圧縮して docs 配下に置き、CLAUDE.md ではそこを参照させるだけにした」など、コンテキスト管理の実践的なノウハウが飛び交いました。また、コンテキスト画像圧縮 OSS の pxpipe（AIエージェントの長文コンテキストを画像として圧縮するツール）への注目も集まっていました。

### 学び

compact の動作を理解していないと、長いタスクで意図せず重要な制約や失敗履歴が失われてしまうリスクがあることを改めて認識しました。「なるべく compact させない範囲で1タスクごとに新規チャットに切り替える」という運用が共有されており、何を言語化すべきかを把握するきっかけにもなるというのは実感が伴う話でした。

## 仕様書駆動開発ツール Speckit の紹介

発表者: totomo さん

「仕様書駆動開発」を実践するためのツール「Speckit」について、概要と主要スキルの紹介がありました。実装より先に仕様を明文化し、その仕様を基準として開発を進めるアプローチをAIエージェントのスキルとして整備したものです。

### どんな内容だったか

Speckit はプロジェクトにスキルとして導入することで、10 個程度のスキルが生成され、仕様の検討から実装までをスキルを順に実行しながら進める設計になっています。主なスキルは以下のような役割を持ちます。

- `/speckit-constitution`: プロジェクトのルールを設定。CLAUDE.md や README.md からプロジェクトのルールを特定し、各仕様作成時の基準となる constitution.md を生成
- `/speckit-specify`: 仕様書を作成する入口コマンド。曖昧な点があれば実行中に質問が来て、回答しながら仕様を明確化していく
- `/speckit-clarify`: specifyで作った仕様の曖昧な点を繰り返し明確化するコマンド。質問が来なくなることを、仕様が明確になったか判断する一つの目安にする
- `/speckit-plan` / `/speckit-tasks` / `/speckit-implement`: 計画→タスク洗い出し→実装までを段階的に進めるコマンド群

### 技術的に面白いポイント

- **仕様書とAIの役割分担**: 仕様書を先に書くことでAIへの指示が明確になり、手戻りが減るという観点
- **段階的な明確化プロセス**: 「clarifyが質問してこなくなること」を仕様が明確になった目安とする仕組みが、仕様の曖昧さを可視化する面白いアプローチ

### 学び

AIエージェントに実装を任せるとき、プロンプトの精度が成果物の品質に直結します。仕様書という形で事前に明文化しておくことで、AIへの指示品質を担保するという考え方は、今後のAI活用でより重要になっていきそうです。一方で、clarifyを繰り返すほど仕様書が肥大化しやすいという課題もあり、どこで「十分」と判断して実装に進むかのバランス感覚が求められる点も議論になっていました。

## AIと日次の振り返り

発表者: mugi さん

「日報を書いているのに振り返りが身になっていない」という課題感から、AIをインタビュアーとして活用した日次の経験学習の取り組みを紹介してもらいました。技術的なトピックでなく、学びのメカニズムそのものに向き合った発表でした。

### どんな内容だったか

発表の出発点は、ギブスのリフレクティブサイクル（1988年）という教育学の知見です。ギブスのモデルでは、経験を「経験する→感情を認識する→評価する→分析する→結論を出す→次の行動を決める」という六つの段階で振り返りますが、日報に書く「やったこと」は「経験する」の記録にしかなっていない、という観察が起点になっています。

そこで AI（Claude）に「経験学習のファシリテーター」役を担ってもらう仕組みを作りました。具体的には終業後にチャット形式で問いかけてもらい、それに答えるインタビュー形式です。ポイントは「AIに意見・アドバイスは言わせない」こと。雑に投げると AI はすぐに「こうしてみよう」と答えを出してきますが、それだと自分の言葉を引き出す前に答えを押し付けられてしまいます。AIをインタビュアーに徹させることで、「考えてはいるけど言語化できていない」自分の内側を掘り起こすきっかけを得る、という設計です。

実際の対話例では、ある出来事を起点に、自分の思考やコミュニケーションのパターンを言語化していく様子が紹介されました。

### 技術的に面白いポイント

- **AIの役割設計**: 「答えを出さず問いかけに徹する」というプロンプト設計で、AIの出力特性を逆手に取っている
- **経験学習理論との接続**: ギブスのリフレクティブサイクルやコルブの経験学習サイクルという既存のフレームワークを、AI活用の設計根拠として使っている点

### 盛り上がったポイント

AIを聞き役にするための指示や、音声対話での活用についても話題になりました。

### 学び

「AI に問いかけ役を任せる」という発想の逆転は参考になりました。AIの答えを受け取るのではなく、AIの問いで自分の思考を動かすという使い方は、学習・内省のツールとして今後も深められそうです。

## betterleaks：シークレット検出ツールの紹介と導入実践

発表者: satoshin さん

gitleaksの後継として登場したオープンソースのシークレット検出ツール「betterleaks」を実際に導入した知見を共有してもらいました。誤検知を減らす工夫や設定ファイルの作り方まで踏み込んだ実践的な内容でした。

### どんな内容だったか

発表によると、広く使われていた gitleaks プロジェクトが現在はセキュリティアップデートのみとなっており、後継として betterleaks が推奨されるようになっているとのことです。betterleaks は正規表現ベースの検出に加え、BPE（Byte Pair Encoding）トークナイザを統計的手法として採用することで誤検知を減らしている点が特徴とのことです。フィルタリングには当初 CEL（Common Expression Language）を使っていましたが、v1.6.0 からは Expr に変更され、可読性・起動速度・バイナリサイズが改善されているとのことです。

発表では実際に `brew install betterleaks` で導入し、Drupal プロジェクトへの適用を試みた際の手順も共有されました。vendor ディレクトリなどのノイズを除外する設定ファイルは AI に作らせたものの、最初は gitleaks 用の設定を生成してきて動かなかったため、公式ドキュメントを参照させて再生成した、という実体験も紹介されていました。

既存の GitHub Secret Scanning と組み合わせた多層的なチェックについても検証しました。

### 技術的に面白いポイント

- **誤検知削減の仕組み**: 単純なパターンマッチではなく、BPE トークナイザによる統計的手法を組み合わせている
- **フィルタリング言語の進化**: CEL から Expr へと短期間で移行するなど、開発が活発で追いかけが必要なレベル感
- **AI によるコンフィグ生成**: 設定ファイルを AI に生成させる際、関連ドキュメントを参照させてから再生成させるアプローチが有効だった

### 盛り上がったポイント

「AIがコードを書いてコミットもどんどん任せていくようになる中で、こういう機械的なガードを厚くしていくことはこれまで以上に大事」という話題で盛り上がりました。組織全体への展開方法についても議論が広がりました。

### 学び

GitHub が提供する Secret Scanning との組み合わせで多段防御になるという観点は参考になりました。AIがコード生成に深く関わるようになるほど、機械的な検知の重要性は増しますし、それを早い段階でローカルのフックに組み込んでおく習慣は広めていきたいと感じました。
