## 汎用性高そうな作図スキルを作った

発表者: nnno さん

AIがまとめてくれた長い文章を、図1枚で掴めるようにする作図スキルを作った、というLT（ライトニングトーク）です。「正しいけれど読んで関係をつかむのは人の仕事」というAI出力の弱点を、図で補う試みでした。

### どんな内容だったか

業務では、全体像を素早く掴みたい場面が意外と多くあります。自分で理解する、他人に説明する、チームで認識を揃える、特定の技術を調べる。ところがAIに調べさせると、出力は文章が中心で、全体像は結局人が組み立てることになります。

例として、ローカルLLMの実行環境をAIに調べさせた約4,800字の結果が、アプリ、呼び出し方、サーバー、推論エンジン、モデル形式、入手元、ハードウェアという層構造の図1枚にまとめ直されました。実際の案件の構成図や、会議で挙がった2案の比較にも使い、初見で分かる図が出たとのことです（「使いやすい」というのは発表者の実感）。

### 技術的に面白いポイント

- **描く前に「何を主張する図か」を1文で書かせる**: 主張が先で、座標は後。結論は本文に書き、図は構造だけを担わせることで、読む量が減ります。
- **MermaidやD2を見送り、座標を指定するSVGにした**: レンダラ任せの配置では、箱の中に2行入れる、特定の箱だけ色を変える、数値を赤で強調するといった操作が思い通りにならなかったそうです。文字サイズ・色・線種を規約で固定することで、描き方のばらつきも抑えています。箱が多い図や総当たりで繋ぐ図はMermaidやD2向きで、使い分けが前提です。
- **スキルとして配布できる**: `/svg-figure` と呼び出すと、文書に載せる説明図をSVGで描きます。Markdown・HTML・docxのどこからでも同じ図を参照できます。

### 盛り上がったポイント

- 「図を作って」とだけ頼むと、図の中に文字を詰め込んでしまうのはLLMあるあるで、「文字の暴力」という言葉に共感が集まりました。
- Mermaidは小さい図でないと人間には見やすくならない一方、依存関係を書けるので、AI向けのドキュメントとしてあえてMermaidで書いている人もいました。ドキュメントの見せ方が、人間向けからAI向けに寄ってきているという指摘も出ました。
- 音声議事録をNotion AIに雑に取らせ、そこから図も作らせる使い方のアイデアが出ました。

### 学び

AIの出力が正しくても、関係をつかむ作業が人に残るなら、読み手の負担は減りません。文章を増やさず、図に構造を持たせるという発想は、自分たちのAI活用にもそのまま当てはまると感じました。

## AI時代のデータエンジニアリング

発表者: shinee

Snowflakeの AIコーディングエージェント「CoCo（Cortex Code）」を使い、データ探索から品質チェック、セマンティックビューの作成、Streamlitでの可視化までを自然言語で進めるデモを交えた発表です。

### どんな内容だったか

データ基盤をSnowflakeとdbtで構築しているチームの視点から、データエンジニアの役割の変化が整理されました。毎回似たパターンのSQLを書く、よくあるエラーを調べる、既存のコードを別環境へ移す、といった繰り返し作業はAIコーディングエージェントが担います。一方で、システム全体への考慮、プロダクトの設計、ガバナンスと信頼性の担保、ビジネス判断は、いまのところ人間に残る仕事です。

発表では、汎用的なAIツールはコンテキストがリポジトリで止まり、テーブル構造やカラムの意味、権限（RBAC）、パイプラインの依存関係を理解しにくいことが課題として挙げられました。CoCoはそれらをユーザーの権限の範囲内で参照し、LLMの推論もSnowflakeのセキュリティ境界内で行われる（外部サービスとのMCP連携を除く）と紹介されました。デモには、dbt Labsが公開している架空の飲食店のサンプルプロジェクト「jaffle_shop」が使われました。

### 技術的に面白いポイント

- **セマンティックビュー**: 物理テーブルと、人やAIが理解しやすい業務概念のあいだに置く層です。デモでは、自然言語で依頼するとビルトインのスキルが動いて質問が返り、答えるとビューが作られました。
- **VQRによる精度向上**: VQRは、検証済みの質問とSQLのペアです。曜日ごとに日数が異なるため、単純合計ではなく「1日あたりの平均売上」で比較する集計ロジックを登録しておくと、曜日別の売上傾向を聞いたときに正しい集計で答えが返ってきます。
- **一気通貫の流れ**: dbtでビルド済みのテーブルを起点に、探索、品質チェック（NULL率・重複・異常値）、セマンティックビュー、ダッシュボードまでを数分で進められると紹介されました。

### 盛り上がったポイント

- 調査用のSQLを人間が考えることはなくなってきた一方、判断は人間に残る、という実感が共有されました。
- 品質チェックを手動でやる場合は、項目ごとにチェック用のSQLを書く手間があります。AIの結果をどこまで信頼するかには悩みがあるものの、手動でも「確認手段そのものが正しいか」を気にする必要があるため、基本は信頼寄りでもよいのでは、という意見が出ました。
- 汎用AIツールとの違いが話題になりました。発表者からは、CLIやMCPではなくSnowflakeのセッション内で動くことや、Snowflakeの運用ノウハウがスキルとして組み込まれていることが挙げられました。
- AIがデータを引っ張ってくる部分は任せ、テーブルやカラムにメタ情報を持たせるなど、AIがうまく働ける土台を整える部分は人間が判断する、という役割分担に納得感がありました。定期的に同じデータを見るならAutomationも設定でき、定型作業をスキルとして共有すれば、これまでエンジニアに依頼していた作業を他のメンバーも実行できます。

### 学び

AIに任せられる範囲が広がるほど、人間の仕事は「AIが正しく働ける情報とルールを整えること」に寄っていくのだと感じました。セマンティックビューやVQRは、まさにその足場づくりにあたります。

## Claude Code の記憶を永続化する：設計と実装

発表者: satozou さん

Claude Codeはセッションをまたぐと文脈が途切れがちです。その課題に対して、HooksとSQLiteで設計判断や課題、作業履歴を構造化して残し、次のセッションで復元する仕組みを作った発表です。

### どんな内容だったか

Claude Codeには、CLAUDE.mdやauto memory（MEMORY.md）といったセッションをまたぐ記憶の仕組みがあります。ただし自由記述のテキストなので、設計判断、課題、ツールの実行履歴を構造化して検索・集計することはできません。会話ログ（JSONL）も一定期間で削除されます。そのため、「先週この設計判断をした理由は？」を毎回説明し直す、といった負担が生じていました。

そこで、SQLiteを中心に、Claude CodeのMemory、Hooks、Goで書いたWebビューアーを組み合わせました。作業中はHooksがファイルの変更差分、Bash・WebFetch・WebSearchの実行ログ、セッションのサマリを自動で記録します。セッション開始時には、Memoryの自動ロードをきっかけにSQLiteを参照し、前回の続きから再開できるようにしています。

### 技術的に面白いポイント

- **Hooksで自動記録し、応答速度に影響させない**: PostToolUseやStopなどのHooksをバックグラウンド（`async`）で実行します。記録に失敗してもClaude Code本体の処理は止まらない作りです。既存の監視の仕組みに影響を与えないよう、Hooksを採用したという判断も共有されました。
- **起動時は軽く、詳細は必要なときだけ**: 毎回すべてを読み込むと、起動時に概算で数千トークンを消費します。そこで、起動時は直前セッションのサマリと件数だけを数百トークン程度で取得し、「前回の課題を確認して」と頼まれたときに詳細を取りに行く二段構えにしています。
- **複数案件を1つの設定で振り分け**: 作業ディレクトリの前方一致で、対応するデータベースを自動的に選びます。未導入のプロジェクトでは何も記録されません。
- **デモ**: AWSのローカルエミュレータ「MiniStack」とローカルLLMのOllamaを組み合わせ、Bedrock風のチャットを動かすデモも紹介されました。

### 盛り上がったポイント

- 「セッションをまたぐと別人になる問題」は以前からあるテーマで、毎回新しい人が来る気持ちで接している、という声がありました。CLAUDE.mdやドキュメントによる補強以外の手段も欲しい、という共感が集まりました。
- 人間は寝ている間に記憶を整理することで肥大化を防いでいるのでは、AIのメモリにも整理の仕組みが必要かもしれない、という指摘がありました。
- チーム全員に効く情報は共有できる形に整備し、手元だけで覚えていればよいことはこの仕組みで貯める。そこから全員に還元すべきものを抽出する、というアプローチも提案されました。
- 昔はAIの面倒を細かく見ていたのでメモが必要だったが、最近は細かく指示しなくてもよくなり、メモを使わなくなったという実感も出ました。
- 別のAIエージェントからClaude Codeを呼び出せるという話には、「その発想はなかった」という反応がありました。常駐して情報を拾い、ストックに整理してくれるAIが身近になる期待と、セキュリティ面の懸念が語られました。

### 学び

記憶の仕組みは、たくさん覚えさせることよりも「何を起動時に読ませ、何を必要なときに取りに行かせるか」の設計が肝だと感じました。モデルの進化で必要な補助が変わっていく、という話も印象的でした。

## PR Stack

発表者: nogumaru さん

GitHubのStacked PRs（PR Stack）が2026年10月に一般提供（GA）となったことを受けて、大きな変更を小さなPRに分け、レビュー待ちの間も次の実装へ進める仕組みをデモ付きで紹介した発表です。

### どんな内容だったか

基盤、API、UIのように順番に依存する変更は、1本にまとめると差分が大きくなり、レビューの質も速度も落ちます。かといって下位PRのマージを待つと手が止まり、手作業でブランチをつなぐと、baseの変更やリベース、CIの確認が煩雑になります。小さく分けるほど、依存関係の運用コストが増えていたわけです。

PR Stackは、同じリポジトリ内で、下のPRを次のPRのbaseにする依存チェーンです。各PRは1つの焦点を持つ小さな差分になり、レビューする人は、その層の変更だけを読めます。GitHubでは2026年7月30日にPublic Previewが始まり、10月6日にGAとなりました。同一リポジトリ内のブランチが前提で、フォークをまたぐ利用には未対応です（発表資料は2026年10月17日時点の確認）。詳細は[GitHubの公式発表](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)と[公式ドキュメント](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs)で確認できます。

### 技術的に面白いポイント

- **GitHub公式のCLI拡張 `gh-stack`**: `gh stack init`で始め、`add`で層を足し、`submit`でpushからPR作成・連結までを行います。AIエージェント向けのスキルとして入れることもできます。
- **親を直したら、上の層へ積み直す**: 下の層を修正したら、`gh stack rebase --upstack`で上位の層へ反映します。コミットのハッシュが変わるため、共同作業者とのタイミングを合わせる必要があります。
- **中段までのマージ**: デモでは、3層のうち中段までをマージすると、その下の層も一緒に取り込まれ、残った最上位のPRはbaseがmainへ付け替わり、その層の差分だけが残ることが示されました。
- **MCPとの関係**: GitHub公式のMCP Serverはあるものの、2026年10月17日時点の公式READMEのツール一覧には、Stack専用の操作は確認できなかったそうです。現状、Stackの操作は`gh stack`が中心です。

### 盛り上がったポイント

- 処理のステップ単位で積むだけでは大きな感動はなかったが、基盤・API・UIのような層（カテゴリ）単位で積む使い方は良さそう、という感想が出ました。
- 手動でリベースすると派生ブランチのコミットハッシュが変わり、PRへのpushにforce pushが必要になります。しかし、リポジトリがforce pushを禁止していると、pushできません。この悩みが解消できそうだ、という声がありました。
- 公式の`gh-stack`スキルが公開されていると知り、「過去の自分がすでに入れていたのを忘れていた」という笑い話も出ました。

### 学び

AIエージェントで並列に実装できる量が増えるほど、変更の依存関係を明示して小さく区切る価値は大きくなります。まずは依存が明確な1機能を3層に分けて試す、という入り方は、すぐに真似できそうだと感じました。

## GitHub管理下の Markdown → Notion Sync

発表者: u3 さん

リポジトリで管理しているMarkdownの仕様書を、Notionへ継続的に同期する方法を調べ、公式のNotion CLIを使った同期ツールを試作した話です。

### どんな内容だったか

あるアプリのCMSにはStrapiを使っており、項目情報（schema.jsonなど）をスクリプトで生成し、詳細仕様とあわせてリポジトリ内のMarkdownで管理しています。バックエンド以外のメンバーも仕様を確認するため、これまではConfluenceに転記していました。ドキュメント管理がNotionに移ったことで、MarkdownからNotionへの同期方法を改めて調べることになりました。

以前の共有会で紹介された移行ツールは、Confluenceからの移行に特化し、API Tokenを使う仕組みでした。API Tokenは今後使えなくなる可能性もあるため、継続的な同期の候補として、Notion MCPと、公開ベータ（Public Beta）のNotion CLIを検討しました。Notion CLIは、API Tokenの発行が不要でOAuth認証を使えるため、こちらを使った同期ツールを作ったとのことです。

### 技術的に面白いポイント

- **Front Matterで同期先を管理する**: Markdownの先頭に、同期先のページやデータベースといったメタ情報を持たせます。
- **ハッシュ値で差分を判定する**: ローカルとNotion側のハッシュ値を比べ、変更があったときだけ同期します。作成と更新はNotion CLIが担います。現在は動作を検証している段階です。
- **MCPより先にツールの存在を確認**: Notion MCP経由での実装を考えていたものの、検証の前に、同様のツールがすでに公開されていることが分かったそうです。

### 盛り上がったポイント

- MarkdownからNotion、NotionからMarkdownという変換は日常的に行うので、よい話題だという声がありました。
- MCPは各自のアカウントで接続すると、触れる範囲が広くなりがちです。読み取りだけで足りるなら、API Tokenのほうが向いているという議論になりました。移行用に発行した強い権限のトークンは、移行が終われば無効化する方針も共有されました。
- OAuthは権限が広すぎることが、最近の課題として話題になりました。スプレッドシート連携でも同様で、サービスアカウントを使う方向で検討しているそうです。
- 丸ごと同期するだけならAPIで済むため、こうしたツールを自作してしまうのは便利でよい、という感想もありました。

### 学び

便利さを優先してOAuthにするか、範囲を絞れるAPI Tokenやサービスアカウントにするかは、自動化の入り口で決めておきたい論点だと感じました。同期の仕組みそのものよりも、「どの権限で動かすか」の設計が重要になる場面は、今後も増えそうです。
